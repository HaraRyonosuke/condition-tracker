# ADR-017: Node.js と npm のマイナー以降の更新

## ステータス

proposed

## コンテキスト

ADR-004 は、Volta で Node.js 26.9.0 と npm 12.1.0 を `package.json` に固定する、と決めている。開始直後は、動かす版を具体的に固定する方を採り、パッチを都度上げる方は採らなかった。

依存パッケージの更新を別途検討するなかで、Node.js と npm についても、同じメジャーの中のマイナーとパッチは積極的に上げたい、という方針が出た。この「マイナーバージョン以降」は、同じメジャー番号のままマイナーとパッチを上げることとする。

あわせて、次の二つが方針に入った。メジャーはバグの温床になりうるので、基本的には上げない。上げるときは別の判断で慎重に進める。マイナーとパッチは、新しい版があるたびにすぐ上げるのではなく、スプリントとスプリントのあいだに確認し、不具合の確認を丁寧にしたうえで上げる。この確認の候補には、Node.js と npm だけでなく、`package.json` の dependencies と devDependencies も含める。

制約は以下の通り。

- 版の固定手段は Volta のままである（ADR-004）。パッケージマネージャーは npm のままである（ADR-002）
- いまのピンは Node.js 26.9.0、npm 12.1.0 である。`engines`、CI（ADR-010）、公開のビルド（ADR-011、ADR-013）もこの Node を指している
- Node.js の奇数メジャーは LTS にならない。ADR-004 は偶数メジャーの 26 を選んでいる
- ピンを上げるときは、手元・`package.json`・CI が別々の版を指さないようにする
- スプリントの区切りは [docs/README.md](../README.md) の機能スプリント、リリーススプリント、サイクル末尾である
- この ADR が accepted になる前は、ピンを変えない

## 選択肢

### 選択肢A: 具体バージョンを固定したまま、上げるときだけ都度判断する

ADR-004 の現状である。

- 長所: いつ動いた版かが残り、不具合の切り分けがしやすい
- 短所: マイナーとパッチが遅れても、誰かが思い出すまで上がらない

### 選択肢B: 同じメジャーのマイナーとパッチは、版が出たら上げる

Node.js は 26 系の新しいマイナーとパッチを上げる。npm は 12 系の新しいマイナーとパッチを上げる。メジャーは別の ADR にする。上げたあとも Volta のピンは残し、`package.json` と CI の指定を同じ変更で新しい版に合わせる。スプリントの途中でも上げる。

- 長所: 同じメジャーの更新に追従できる。ピンは残るので、リポジトリを開いたときの版はなお一つに決まる
- 短所: 作業の途中で版が動くと、機能の不具合と版の不具合が混ざる。更新のたびに `package.json`、`engines`、CI の指定を一緒に直す。Current 期間の不具合も取り込みうる

### 選択肢C: メジャーも含めて最新へ追う

- 長所: 版の遅れが最も小さい
- 短所: 次のメジャーで、CI と公開ビルドがいまの Node 26 前提から外れる。奇数メジャーは LTS にならない、という ADR-004 の理由も一度に崩れる。メジャーはバグの温床になりうる

### 選択肢D: スプリントのあいだに確認し、同じメジャーのマイナーとパッチは上げる

一つのスプリントが終わり、次のスプリントに入る前に、下の確認候補の更新を見る。機能スプリントとリリーススプリントのあいだも、その次に入る前も、同じ確認である。スプリントの途中では上げない。

Node.js と npm は、同じメジャーのマイナーとパッチがあれば上げる。ほかのパッケージは、更新の有無を見て、上げるか据え置くかを GitHub issue に書く。上げるものについては、インストール、型検査、lint、単体テスト、ビルドが、上げた版で通ることを見る。不具合があれば、その回は据え置き、理由を issue に書く。Node.js と npm を上げたあとも Volta のピンは残し、`package.json` と CI の指定を同じ変更で揃える。

メジャーは基本行わない。行うときは、この確認とは別の ADR で、影響を見てから進める。

- 長所: 作業中の版は固定されたままである。同じメジャーの遅れは、スプリントをまたいで残さない。不具合は、上げる手順の中で見る
- 短所: あいだの確認を飛ばすと、選択肢Aと同じく遅れが残る。確認は選択肢Bより長い

## 確認候補

スプリントのあいだに見るものは、次である。

- Node.js（Volta と `engines`。いまは 26.9.0）
- npm（Volta。いまは 12.1.0）
- dependencies: `@lucide/vue`、`pinia`、`vue`
- devDependencies: `@eslint/js`、`@tailwindcss/vite`、`@tsconfig/node24`、`@types/node`、`@vitejs/plugin-vue`、`@vue/tsconfig`、`eslint`、`eslint-config-prettier`、`eslint-plugin-vue`、`globals`、`npm-run-all2`、`prettier`、`tailwindcss`、`typescript`、`typescript-eslint`、`vite`、`vite-plugin-vue-devtools`、`vitest`、`vue-tsc`

パッケージの追加と削除は `package.json` に合わせ、その回の GitHub issue に書く。

Node.js と npm は、同じメジャーのマイナーとパッチがあれば、不具合の確認をしたうえで上げる。ほかのパッケージは、同じタイミングで更新の有無を見る。上げるか据え置くかは、その回の issue に書く。

## 決定

選択肢Dを採る。確認候補は、スプリントのあいだに見る。Node.js と npm は、同じメジャーのマイナーとパッチを、不具合の確認をしたうえで上げる。ほかのパッケージは、同じ確認で更新の有無を見て、上げるか据え置くかを issue に書く。メジャーは基本行わない。

## 理由

同じメジャーの中の遅れは残したくない。一方で、スプリントの途中に版が動くと、いま作っているものの不具合と、版の不具合が混ざる。確認のタイミングをスプリントのあいだに置き、上げるときは既存の検査を通す、が両方を取る。

再現性は、追従をやめることではなく、上げた版を Volta のピンとして残すことで足りる。ADR-004 がパッチの都度更新を退けたのは、開始直後に切り分けを優先したためである。いまの方針は、その固定の仕組みを残したまま、確認のタイミングと確認の丁寧さを決めて追う、に変える。

メジャーはバグが出やすい。選択肢Cのように、この確認の列へは入れない。行うときは、CI と公開ビルドが Node 26 を前提にしていることを見直す ADR に分ける。

## 結果

- accepted になったあと、スプリントとスプリントのあいだに、確認候補を見る。Node.js の 26 系と npm の 12 系に新しいマイナーまたはパッチがあれば、インストール、型検査、lint、単体テスト、ビルドを見たうえで上げる。ほかのパッケージは、更新の有無と、上げるか据え置くかを issue に書く
- スプリントの途中ではピンを変えない
- 不具合で据え置いたときは、その理由を GitHub issue に書く。上げたときも、どの版にしたかを同じ場所に書く
- ピンを上げるときは、`package.json` の Volta と `engines`、CI の Node 指定を、同じ変更で揃える
- メジャーは基本行わない。行うときは別の ADR で慎重に進める
- ADR-004 の Volta と、偶数メジャー 26 を選んだことは残す。ADR-004 の「パッチは都度上げない」は、本 ADR が accepted になった時点で置き換わる。ADR-004 全体は superseded にしない
- accepted になる前は、26.9.0 と npm 12.1.0 のピンを変えない
