# ADR-004: Node.js のバージョン管理

## ステータス

accepted

## コンテキスト

ADR-003 で実装と実行を自前PCのローカル環境で行うことにした。
ローカルでは Node.js の版がマシンやインストール方法でずれやすい。
プロジェクト開始時点で版の決め方を固定しておかないと、後から動かなくなったときに
「環境の差」と「コードの問題」を切り分けにくくなる。

制約は以下の通り。

- Windows 上の個人開発である
- バージョン管理ツールとして Volta は導入済みである
- パッケージマネージャーは ADR-002 で npm を採用している
- プロジェクトは開始直後であり、後からメジャーバージョンを上げる作業は少ない方がよい
- 小規模な個人プロジェクトであり、ツール自体の学習コストは低く抑えたい
- Node.js の偶数メジャーは LTS になる系統だが、リリース直後は Current である

## 選択肢

### 選択肢A: Volta

- 長所: 導入済み。`package.json` に版を書けるので、リポジトリを開いた時点で使う版が分かる。npm の版も同じ仕組みで固定できる
- 短所: ツールが増える。Volta を入れていない環境ではピンの効き方が分からない

### 選択肢B: nvm-windows

- 長所: Windows での利用例が多い。情報を探しやすい
- 短所: シェルごとに切り替える運用が中心で、リポジトリに版が残りにくい。未導入なので学習コストが乗る

### 選択肢C: fnm

- 長所: 切り替えが速く、nvm 系に近い使い方ができる
- 短所: 未導入。この規模で速さを取る理由が薄い。リポジトリに版を残す方法も、Volta ほど手順が短くない

### 選択肢D: 公式インストーラだけで入れる

- 長所: 追加ツールが不要。インストール手順が短い
- 短所: プロジェクト単位の固定がない。将来マシンを変えたときや、自分でもう一度入れ直したときに版がずれやすい

### 固定する Node.js の版

バージョン管理ツールと別に、どの系統を固定するかも決める必要がある。

- 版A: いまの Active LTS（24系）を固定する
- 版B: 偶数メジャーの最新（26.7.0）を固定する
- 版C: メジャーだけ決め、パッチは都度上げる

## 決定

Volta を使い、Node.js 26.7.0 と npm 12.0.2 を `package.json` に固定する。

## 理由

バージョン管理ツールは、すでに入っている Volta が制約に対して一番負荷が低い。
ADR-002 で npm を使う方針とも矛盾しない。`package.json` に版が残るので、
「このリポジトリではこの版」が文書以外でも追跡できる。

nvm-windows と fnm は未導入で、リポジトリへの固定という目的に対して追加の手順が増える。
公式インストーラだけだと、開始直後は楽だが、版の根拠がリポジトリに残らない。

Node.js の版は、開始直後なので 24系を今固定すると、26 が LTS になったあとに上げる作業が来る。
26.7.0 は 2026年8月時点では Current であり、Active LTS になるのは同年10月予定である。
偶数系統の最新を今取ると、後から 24→26 へ上げる作業を避けられる。
その代わり、LTS 昇格までの間は Current 期間の更新を受け入れる。

「偶数だからいま安定版」ではない。偶数は LTS になる系統であり、26 はまだその途中である。
奇数メジャーは LTS にならないため選ばない。

パッチを都度上げる運用（版C）は、再現性より追従を優先する。開始直後の切り分けやすさを取るなら、
いま動かす具体バージョンを固定する方が合う。

## 結果

- リポジトリを開いたときに使う Node.js / npm の版が `package.json` から分かる
- 自前PCでのセットアップ手順が、バージョン管理ツールの分だけ増えることを受け入れる
- 2026年10月の LTS 昇格までは、26系が Current である前提で更新を追う
- `engines` の指定は、この固定方針に合わせて後で揃える
- バージョン管理の前提が変わった場合は、本ADRを superseded にして再検討する
