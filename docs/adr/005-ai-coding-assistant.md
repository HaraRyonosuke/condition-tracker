# ADR-005: AI開発支援ツールの選定

## ステータス

proposed

## コンテキスト

ADR-003 で実装と実行を自前PCのローカル環境で行うことにした。
これまでは Claude（チャット）で設計の壁打ちをしながら進めていたが、
ローカルのリポジトリを直接読み書きする開発支援を、どのツールで行うかを決める必要が出てきた。

使い慣れていたのが Claude（チャット）だけだったため、そこから開発を始めた。
Claude Code を使い始めるタイミングで、開発向けエージェントへの移行も検討した。

開発を続けていると Claude のセッション制限にすぐ達し、作業が止まりやすかった。
AI 開発の練習をするなら、開発の範囲では制限で止まらない容量がほしい。
既存の Claude プランを上げるより、開発向けのエージェントを新たに契約する方が費用を抑えられる、
という見立てが移行を検討したきっかけである。

このプロジェクトはアプリを完成させることだけが目的ではない。
設計判断の過程を自分で踏み、文書に残す練習でもある。
ツールの選び方が、判断を自分で書くか、生成結果を追認するかの比重を変える。

制約は以下の通り。

- 主目的は、動く成果物に加えて、要件・技術選定・ADR を自分の言葉で残すことである
- Vue 3 と TypeScript の実装経験はあるが、上流設計の経験は浅い
- ここまでの設計会話は Claude（チャット）で行っていた
- Claude（チャット）以外の開発エージェントは使い慣れていなかった
- Claude Code を使い始めるタイミングで、移行先も合わせて検討した
- 開発の練習として、セッション制限で作業が止まりにくい容量がほしい
- 既存プランの上位契約より、費用を抑えたい
- 同じ契約の中で複数モデルを試せると、モデルの比較がしやすい
- ADR-003 の結果、作業場所は自前PC上のローカルリポジトリである
- 公開リポジトリであり、文書に個人的・医療的な記述は含めない
- 小規模な個人プロジェクトであり、複数ツールの併用コストは低く抑えたい

## 選択肢

### 選択肢A: Claude（チャット）を中心にする

- 長所: すでに使い慣れている。設計の壁打ちや文章の整理がしやすい
- 短所: セッション制限で開発が止まりやすい。リポジトリの検索・編集・コマンド実行が手元と分断される。判断と実装の根拠がチャット側に残り、リポジトリ側の履歴とずれやすい

### 選択肢B: Cursor を中心にする

- 長所: ローカルリポジトリを開いた状態で、検索・編集・コマンド実行まで続けて頼める。ADR と実装の差分を同じ場所で確認できる。開発向けのエージェントであり、契約に複数モデルが含まれるため比較しやすい
- 短所: 生成が速いため、判断を書かずに実装へ進みやすい。使い方を自分で制約しないと、レビューが追認になりやすい

### 選択肢C: GitHub Copilot を中心にする

- 長所: エディタ上の補完が強く、慣れた実装作業の速度が上がる
- 短所: 長い設計会話や ADR の論理レビュー向きではない。判断の言語化という主目的に対して、支援の範囲が狭い。セッション制限の解消というきっかけにも直接は応えない

### 選択肢D: AI 支援を使わない

- 長所: 判断も実装も自分の手だけに残る。生成物の追認が起きない
- 短所: 上流設計の練習速度が落ちる。レビュー役がいないと、制約と理由の穴に自分で気づきにくい

## 決定

開発支援の中心は Cursor にする。
リポジトリを触らない壁打ちだけが必要なときは、Claude（チャット）を補助として使ってよい。
GitHub Copilot は導入しない。

## 理由

移行を検討した直接の理由は、Claude のセッション制限で開発練習が止まりやすかったことである。
プランを上げて容量を足すより、開発向けエージェントを新たに契約する方が費用を抑えられる、
という制約の下で候補を探した結果、Cursor に至った。

ADR-003 で作業場所がローカルリポジトリになった以上、
リポジトリを開けないチャットだけを中心にすると、編集と根拠がまた分断される。
Cursor は検索・編集・実行が同じ場所で完結し、今回の活用範囲（リポジトリ上の設計と実装）に合う。
契約に複数モデルが含まれることも、モデル選定の練習をする制約と両立する。

主目的は完成速度ではなく判断の言語化なので、Cursor に全部書かせて追認する運用にはしない。
判断（選択肢・制約・決定）は自分で行い、実装の下書きや文書の論理チェックを Cursor に頼む。
この分担を守れるなら、短所である「先に実装してしまう」は運用で抑えられる。

選択肢Aは設計会話には向くが、制限と費用、ローカル開発との分断が残る。
中心にはせず、リポジトリ編集が不要な壁打ちに限って補助に残す。
Claude Code を選ばなかったのは、当時使い慣れていたのが Claude だけであり、
Code に進むタイミングで Cursor への移行を検討したためである。
制限と費用の見立ては、その比較では Cursor の方が合うと判断した。

選択肢Cは補完としては有用だが、ADR のレビューや設計判断の組み立て、
セッション制限の解消のいずれにも中心として足りない。

選択肢Dは独立性は高いが、上流設計が浅いという制約の下では、
穴の指摘が得られず学習効率が落ちる。主目的に対して合理的ではない。

## 結果

- ローカルリポジトリ上で、設計文書と実装の差分を同じツールで扱える
- 開発の練習に必要な容量を、既存プランの上位契約より費用を抑えて確保する
- 同じ契約の中で複数モデルを比較できる
- 判断の本文は自分で書き、Cursor は下書き作成や論理の指摘に使う、という分担になる
- Claude（チャット）は、リポジトリを触らない壁打ちに限定する
- 生成が先行しやすいことは受け入れ、判断を先に文書化してから実装する運用で抑える
- 支援ツールの前提が変わった場合は、本ADRを superseded にして再検討する
