# ADR-015: push 前に仕様を当てる順

## ステータス

accepted

## コンテキスト

push 前のリファクタは、ツールごとの仕様を [docs/specs/](../specs/README.md) の順で差分に当てる。
仕様が増えると、前の段の直しを後ろの段が崩す。PascalCase や `use...Store` のような形と、未使用の削除や名前の変更は、同じファイルに当たる。

制約は以下の通り。

- フレームワークごとの仕様（Vue、Pinia、Vite、TypeScript、Vitest）は残す
- 全体の形（PascalCase、自己閉じ、kebab-case など）は、フレームワークの仕様とは別に置く
- 関係しない仕様は飛ばす。範囲の外は触らない。外から見た動きは変えない
- 同じ行を別の理由で書き換える指定は、順だけでは解消しない

## 選択肢

### 選択肢A: ツール仕様を先に、一般リファクタを最後にする

Vue から Vitest まで先に当て、未使用や名前の掃除は最後に行う。

- 長所: ツールの書き方が先に揃う
- 短所: 最後の名前変更が PascalCase や `use...Store` を崩す。Tailwind が切り出した部品は、その回の Vue の形を通らない

### 選択肢B: 緩いものから当て、形を後ろの段で整える

一般リファクタを先にし、Tailwind、全体の形、Vue、Pinia、Vite、TypeScript、Vitest の順にする。フレームワークごとの仕様は残す。

- 長所: 名前や部品を動かしたあとで、形の仕様が整える。切り出した `.vue` にも PascalCase とフル形式が当たる
- 短所: 新しい仕様を足すとき、前か後ろかの判断が要る。同じ行を別理由で書き換える指定は、この順でも残る

### 選択肢C: 今の順のまま、形だけ二度目に当てる

1巡目はツール仕様、2巡目は Tailwind と Vue の形と Pinia だけをもう一度当てる。

- 長所: 既存の並びを崩さない
- 短所: 同じ仕様を二回読む。表が長くなる

## 決定

選択肢Bとする。順の正は [docs/specs/README.md](../specs/README.md) である。

## 理由

効く制約は、フレームワークごとの仕様を残すことと、後ろの段が前の段の形を整えることである。
選択肢Aは最後の一般リファクタが形を崩す。選択肢Cは干渉を直すが、読む回数が増える。
選択肢Bは、対象が広いものと部品を新しく作るものを前に、書き方を狭く決めるものを後ろに置く。

同じ行を別の理由で書き換える指定は、順では解消しない。そのときは仕様の文面を片方に寄せる。

## 結果

- 順の一覧は [docs/specs/README.md](../specs/README.md) の表だけを更新する。この ADR には順を書き写さない
- フレームワークごとの仕様ファイルは残す。全体の形は [docs/specs/form.md](../specs/form.md) に置く
- 新しい仕様は、対象が広いもの、または部品や名前を新しく作るものを前に、書き方を狭く決めるものを後ろに足す
- 箇条の正は各仕様ファイルのままである。この ADR は順の理由だけを持つ
