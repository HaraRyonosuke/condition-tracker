# ADR-014: 画面確認の場

## ステータス

proposed

## コンテキスト

画面の見た目を確認する場が要る。Figma に残す方が、後からデザインを辿れる。一方、このリポジトリは無料の範囲で開発しており、Figma の API 制限に当たって確認が止まる。

スタイリング手段は Tailwind である（ADR-007）。この ADR は色や部品の選定ではなく、確認をどこで行うかだけを決める。実装後の動作確認は、ブラウザでその操作を通すこととは別である。

制約は以下の通り。

- 無料の範囲で開発する。Figma の API 制限に当たる呼び出しはしない
- 残る記録としては Figma の方がよい、という判断は捨てない
- 既存の Figma リンクは消さない
- 画面の操作確認はブラウザで行う。確認の場がそれを置き換えない
- 公開リポジトリであり、文書に個人的・医療的な記述は含めない

## 選択肢

### 選択肢A: Figma を確認の正にする

画面確認は Figma で行う。API 制限は都度避ける。

- 長所: デザインが Figma に残る
- 短所: 無料枠の API 制限で確認が止まる。制限を避ける手順が増える

### 選択肢B: Canvas だけにし、Figma の記録は捨てる

確認も記録も Cursor Canvas にする。既存の Figma リンクは消す。

- 長所: 確認の場が一つになる
- 短所: 残る記録としては劣る、という判断を捨てる。既存のリンクが辿れなくなる

### 選択肢C: 確認は Canvas、記録としての Figma は残す

画面・レイアウト・見た目を見せるときは Cursor Canvas を使う。Figma のファイルや API は開かない。既存リンクは残し、確認のためには辿らない。制限が外れたらこの ADR を見直す。

- 長所: API 制限を避けつつ、Figma を残した方がよいという判断を保てる
- 短所: 確認の場と、残したい記録の場が分かれる。Canvas は Figma の代替記録にはならない

## 決定

選択肢Cとする。画面確認の正は Cursor Canvas である。Figma は API を呼ばず、既存リンクは残す。

## 理由

効く制約は、無料枠の API 制限で確認を止めないことと、Figma の方が残る記録としてはよいという判断を維持することである。
選択肢Aは制限に当たる。選択肢Bは、その判断を捨てる。
選択肢Cは確認だけを Canvas に移し、記録の評価は変えない。

## 結果

- エージェントの手順は [`.cursor/rules/ui-canvas.mdc`](../../.cursor/rules/ui-canvas.mdc) に置く
- 実装を変えたあとの動作確認はブラウザのままである
- 制限が外れたら、確認の場を Figma に戻すかこの ADR を見直す
