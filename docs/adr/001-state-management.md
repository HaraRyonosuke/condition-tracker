# ADR-001: 状態管理ライブラリの選定

## ステータス

accepted

## コンテキスト

本アプリでは、入力フォームの状態、記録データの一覧、グラフ表示用のデータなど、
複数のコンポーネント間で状態を共有する必要がある。

Vue 3のComposition APIのみで管理することも可能だが、
状態管理の方針を明示的に決めておかないと、
イテレーションを重ねるにつれてデータの流れが追いにくくなる。

制約は以下の通り。

- プロジェクト規模が小さく、大規模な状態管理機構は過剰になる可能性がある
- Vuexの使用経験はあるが、Piniaは公式ドキュメントを参照した程度である
- TypeScriptとの型安全な統合が求められる

## 選択肢

### 選択肢A: Pinia

- 長所: Vue 3の公式推奨ライブラリ。TypeScriptとの親和性が高く、型推論が効く。Vuexと比べてAPIがシンプルでボイラープレートが少ない
- 短所: 使用経験がなく、学習コストが発生する

### 選択肢B: Vuex 4

- 長所: 使用経験があり、学習コストがかからない。情報量が多い
- 短所: Vue 3ではPiniaが公式推奨に移行しており、新規プロジェクトでの採用事例が減少している。TypeScriptとの統合がPiniaより煩雑

### 選択肢C: Composition API（provide/inject）のみ

- 長所: 追加ライブラリが不要。小規模アプリには機能的に十分
- 短所: 状態管理の構造が暗黙的になりやすく、規模が拡大した際に破綻するリスクがある

## 決定

Piniaを採用する。

## 理由

Vue 3エコシステムにおける現在の標準であり、
今後このプロジェクトを拡張する場合も、他プロジェクトに知見を転用する場合も、
Piniaを選択しておく方が汎用性が高い。

学習コストは発生するが、アプリの規模が小さいため
ストア設計が複雑化する可能性は低く、コストは限定的と判断した。

選択肢Cは現時点の規模では機能的に成立するが、
状態管理の方針が暗黙的になることで、
後続のイテレーションで設計判断が追跡できなくなる懸念があるため採用しない。

## 結果

- Piniaの学習コストを受け入れる
- ストア設計がドキュメント化可能な形で明示される
- Vuexでの経験を活かしつつ、現行の標準的なAPIに移行できる
- 将来的に状態管理の要件が変化した場合は、本ADRをsupersededとして再検討する
