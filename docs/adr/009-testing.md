# ADR-009: 単体テストと総合テスト

## ステータス

accepted

## コンテキスト

US-01 の機能はローカルで確認済みである。リリース前の「テスト」に何を含めるかを決める必要がある。
型チェックと lint はあるが、文面の整形や合計の計算を機械が繰り返す手段はまだない。
ブラウザ自動操作（E2E）を必須にすると、一周目の1画面にしては導入と維持が大きい。

制約は以下の通り。

- リリース前に単体テストと総合テストは行いたい
- 厳密さ（網羅率 100%、全画面の自動操作）は必須ではない
- 公開後に問題が出たら直して出し直す（パッチ）でよい
- 個人プロジェクトであり、道具の数は抑えたい
- クリップボードと HTTPS は localhost と挙動が違いうる

## 選択肢

### 選択肢A: 型チェックと lint だけ

- 長所: 追加の依存がない。いまの機能スプリントと一致する
- 短所: コピー文面の回帰を機械が見ない。リリース前の単体が空になる

### 選択肢B: 薄い単体（Vitest）と、本番 URL での人手の総合。E2E 自動は入れない

- 長所: 純関数の文面・計算を短時間で繰り返せる。総合は利用者が触る面そのもので見る。導入が小さい
- 短所: 画面操作の自動再現はない。カバレッジは意図的に薄い

### 選択肢C: 単体に加えて E2E（Playwright など）をリリース必須にする

- 長所: クリックからコピーまでの脚本を残せる
- 短所: セットアップと画面変更への弱さが、一周目の規模に対して大きい

## 決定

選択肢Bとする。

- **単体**: Vitest。画面を開かない確認。コピー文面の整形など、効く関数を数本。網羅は追わない
- **総合**: 利用者が触る本番 URL（HTTPS）で、その US の受け入れを人が行う。これがリリース前の総合テストである
- **E2E 自動**: 今は入れない。総合の操作が何度も負担になったら再検討する。スクレイピング系ツールは使わない

US-01 は、初回の本番確認より前に Vitest を薄く入れる。

公開後の不具合は、修正して短い再デプロイとし、[docs/releases/](../releases/) に残す。

## 理由

効く制約は、リリース前に単体と総合を置くことと、厳密さを求めないことである。
選択肢Aは単体が空である。選択肢Cは一周目の1画面に対して維持コストが大きい。
選択肢Bは、すでに決まっている本番 HTTPS 確認を総合とし、機械側は純関数に限る。

## 結果

- 機能スプリントの「テスト」は、少なくとも `type-check`、lint / format、Vitest の単体である
- リリース前の総合は、本番 URL での人手確認である（ホストの ADR ができたあとその URL）
- ルートに E2E 用のブラウザ自動は置かない
- デプロイ先のサービス名は、本 ADR では決めない
