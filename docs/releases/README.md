# リリースノート

デプロイ単位で、**何が変わったか**を短く残す。ADR（なぜ）とは別物。このディレクトリが変更履歴の正である。ルートの `CHANGELOG.md` は置かない。

- ファイル名の例: `US-01.md`（機能リリース）、`redeploy-2026-08-25.md`（設定変更なしの再デプロイ）
- 振り返りの「リリース」見出しと対応させる
- GitHub Releases を出すたびに1件作る。本文は短い要約と、このディレクトリの該当ファイルへのリンク
- ソースコードのアーカイブはこちらから添付しない。GitHub がタグに付ける Source code (zip / tar.gz) は消せないが、配布物としては使わない
- バックエンド開始後の成果物（バイナリ、コンテナなど）を付けるかも、今は決めない。検討に留め、各リリース時に判断する
- アプリ画面や X への埋め込みはしない
- 本番 URL での総合結果は、その回のノートの「確認」に残す。通った / 失敗 / 未実施を書く

## テンプレート（機能リリース）

```markdown
# US-xx リリースノート

- 日付: YYYY-MM-DD
- 公開面: （本番 URL）
- GitHub Release: （URL。出したあと）
- 含む US: US-xx

## 利用者向け

- （できるようになったこと）

## 技術

- （主な変更。依存・設定）

## 確認

- 日時: YYYY-MM-DD
- 公開面: （本番 URL）
- 環境: （ブラウザ）

| 項目                 | 結果                             |
| -------------------- | -------------------------------- |
| （入力・コピーなど） | 通った / 失敗 / 未実施。短い事実 |

## 既知・注意

- （ブラウザ、クリップボード権限、未対応）
```

## テンプレート（設定変更なし・再デプロイのみ）

```markdown
# 再デプロイ YYYY-MM-DD

- 公開面: （本番 URL）
- GitHub Release: （URL。出したあと）
- 含む変更: （merge 済み PR または US 名。機能差分がなければ「前回と同内容」）
- 設定変更: なし
- 確認: 本番 HTTPS で（入力・コピーなど、触った項目だけ）。結果を上の表と同じ粒度で残す
```
