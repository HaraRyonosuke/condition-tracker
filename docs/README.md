# プロジェクトドキュメント構成

このディレクトリには、設計判断のプロセスと根拠を記録するためのドキュメントを格納する。

## 構成

```
docs/
├── README.md                     # このファイル
├── requirements.md               # 課題定義・ユーザーストーリー
├── design.md                     # 画面設計・データモデル設計（Mermaid図含む）
├── conventions.md                # 人向けコーディング規約（一部確定）
└── adr/                          # Architecture Decision Records
    ├── 000-template.md           # ADRテンプレート
    ├── 001-state-management.md   # 状態管理ライブラリの選定
    ├── 002-package-manager.md           # パッケージマネージャーの選定
    ├── 003-development-environment.md   # 開発環境の選定
    ├── 004-node-version-management.md   # Node.js のバージョン管理
    ├── 005-ai-coding-assistant.md       # AI開発支援ツールの選定
    ├── 006-data-persistence.md          # データの保存と持ち出し
    ├── 007-styling.md                   # スタイリング手段の選定
    └── 008-lint-format.md               # コード規約（Lint とフォーマット）
```

## スプリントの進め方

イテレーションとスプリントは同じ単位とする。ユーザーストーリー単位で区切り、1スプリント = 1ブランチ = 1プルリクエスト（[design.md](./design.md) の実装方針）。

各スプリントは次の7段階を**セット**で進める。途中の段階を飛ばして閉じない。製品全体を先に書き切ってから実装する、という意味ではない。基本設計と詳細設計は**そのスプリントのスコープ**に限る。

```mermaid
flowchart LR
  basicDesign[基本設計]
  detailedDesign[詳細設計]
  implementation[実装]
  testing[テスト]
  production[本番環境への導入]
  verification[確認]
  retrospective[振り返り]
  basicDesign --> detailedDesign --> implementation --> testing --> production --> verification --> retrospective
```

| 段階             | やること                                                         | このリポジトリでの置き場                                                                               |
| ---------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 基本設計         | 誰の何を解くか、成功なら何ができるか、やらないこと               | [requirements.md](./requirements.md) の対象ストーリー。スコープの目的と「やらないこと」                |
| 詳細設計         | 画面・データ・コピー文面・技術判断                               | [design.md](./design.md)、必要な [ADR](./adr/)、必要なら [conventions.md](./conventions.md)            |
| 実装             | スコープどおりのコード                                           | `src/` と設定。目的から外れる実装は足さない                                                            |
| テスト           | 壊れていないことを、そのスプリントで決めた手段で見る             | 少なくとも `type-check` と lint / format。自動テストの枠は未導入なら、そのスプリントで入れるかを決める |
| 本番環境への導入 | 利用者が触る場所へ出す                                           | デプロイ先は未固定。この段階を飛ばしてスプリントを閉じない                                             |
| 確認             | 本番（またはそれに相当する公開面）で、受け入れ条件を満たすか見る | 入力・コピーなど、そのスプリントの成功条件                                                             |
| 振り返り         | うまくいったこと、持ち越し、次で変えること                       | 短く残し、次スプリントの基本設計に使う                                                                 |

実装中に判断が出たら、先に ADR / `design.md` を更新してからコードを続ける。

## ドキュメントの書き進め方

スプリント内の基本設計・詳細設計で、次を行う。

1. **requirements.md** に、そのスプリントで解く「誰の・何の問題を・なぜ解くか」を書く
2. 技術的な判断が必要になるたびに **ADR** を1件書く
3. 実装に入る前に **design.md** で画面とデータ構造を整理する
4. 同じタイミングで、そのスコープの目的と「やらないこと」を短く固定する（余分な実装を防ぐ）
5. 判断が変わった場合は、古いADRのステータスを `superseded by ADR-XXX` に変更し、新しいADRを起こす

## ADRのステータス

| ステータス              | 意味                               |
| ----------------------- | ---------------------------------- |
| `proposed`              | 提案中。まだ確定していない         |
| `accepted`              | 採用。この判断で進める             |
| `deprecated`            | 非推奨。この判断はもう有効ではない |
| `superseded by ADR-XXX` | 別のADRに置き換えられた            |

## 運用方針

- 完璧を目指さない。「その時点での判断」を記録することが目的
- 判断が後から変わることは想定内。変更の経緯が追跡できることに価値がある
- ドキュメントは実装中の判断でも更新する。製品全体を書き上げてから実装に入る、という進め方はしない
- スプリントは「スプリントの進め方」の7段階をセットで進める。基本設計・詳細設計はそのスプリントの範囲に限る
- 先のストーリー用に ADR 番号を予約しない。必要になった時点の次番号を使う
